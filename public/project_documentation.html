🎯 Gambaran Umum Project

Apa itu LMC?

Legian Medical Clinic (LMC) adalah sistem informasi manajemen klinik medis yang dibangun menggunakan framework Laravel 12. Aplikasi ini dirancang untuk memfasilitasi dua kelompok pengguna utama: pengunjung website (pasien dan calon pasien) serta tim administrasi klinik (owner dan admin).

Sistem ini menyelesaikan berbagai masalah umum yang dihadapi klinik medis dalam pengelolaan informasi digital. Pertama, memberikan informasi yang lengkap dan mudah diakses kepada pengunjung tentang layanan medis, dokter, dan lokasi klinik. Kedua, memudahkan tim administrasi dalam mengelola konten website tanpa perlu keahlian teknis yang mendalam. Ketiga, menyediakan konten dalam dua bahasa untuk menjangkau audiens yang lebih luas.

🌐 Landing Page (Public)

Landing page adalah website publik yang bisa diakses oleh siapa saja tanpa perlu login. Halaman ini dirancang dengan user experience yang optimal, menampilkan informasi penting secara hirarki. Pengunjung pertama kali akan disambut dengan banner hero yang eye-catching, diikuti dengan section-section informatif seperti About (tentang klinik), Services (layanan medis), Doctors (profil dokter), Gallery (foto-foto klinik), Articles (artikel kesehatan), dan Contact (informasi kontak dengan peta lokasi).

💡 Fitur Unik: Preference Modal
Ketika pengunjung pertama kali membuka website, mereka ditanya "Apa yang Anda cari hari ini?" dengan pilihan Services, Doctors, Contact, atau All. Berdasarkan pilihan ini, halaman akan auto-scroll ke section yang relevan, mengurangi friction dan membuat pengunjung cepat menemukan informasi yang mereka butuhkan.

👨‍💼 Admin Panel (Private)

Admin panel adalah dashboard khusus untuk tim internal klinik yang hanya bisa diakses setelah login. Panel ini memiliki sistem Role-Based Access Control (RBAC) yang membedakan hak akses antara Owner dan Admin. Owner memiliki akses penuh termasuk mengelola user, sementara Admin hanya bisa mengelola konten website.

Dari admin panel, tim klinik bisa mengelola semua aspek konten tanpa perlu menyentuh code. Mereka bisa update informasi header, mengubah deskripsi about, menambah layanan baru, mengupload foto dokter, membuat artikel kesehatan, mengatur galeri foto, dan mengupdate informasi kontak - semuanya melalui form yang user-friendly.

Penjelasan Arsitektur Layer

Frontend Layer menghandle semua yang dilihat dan diinteraksi oleh user. Blade sebagai template engine memungkinkan kita menulis HTML dengan dynamic data dari backend. Bootstrap 5 menyediakan komponen UI yang responsif sehingga website tampil baik di desktop maupun mobile. JavaScript vanilla digunakan untuk interaktivitas seperti modal, form validation, dan smooth scrolling - tanpa dependency framework berat sehingga loading tetap cepat.

Pemilihan Blade templates bukan tanpa alasan - sebagai template engine bawaan Laravel, Blade menawarkan perfect integration dengan ecosystem Laravel, syntax yang clean dan readable, serta performance yang excellent karena templates di-compile menjadi pure PHP. Bootstrap 5 dipilih karena mature component library-nya yang sudah battle-tested, extensive documentation, dan support komunitas yang besar. Untuk JavaScript, kita deliberately avoid heavy frameworks seperti React atau Vue karena complexity yang ditambahkannya tidak justified untuk use case ini - vanilla JS sudah cukup powerful untuk kebutuhan interactivity yang sederhana.

Application Layer adalah inti dari logika bisnis. Laravel 12 framework menyediakan struktur MVC yang rapi. Controllers menghandle HTTP requests dan responses, Models merepresentasikan data dan relasi database, Views menampilkan data dalam format HTML. Services adalah class khusus yang mengextract logika bisnis kompleks (seperti translation, analytics, image processing) agar Controllers tetap slim.

Service Layer pattern adalah crucial architectural decision di project ini. Tanpa services, semua business logic akan tercampur di controllers, making them fat dan hard to test. Dengan mengextract logic ke dedicated service classes, kita achieve better separation of concerns, code reusability (service bisa dipanggil dari multiple controllers), dan easier unit testing (service classes bisa di-test independent dari HTTP layer). Contohnya TrendAnalysisService menghandle semua kompleksitas trend score calculation - controllers cukup call service method tanpa perlu tau detail algorithmnya.

Data Layer menghandle persistence. Eloquent ORM memungkinkan kita berinteraksi dengan database menggunakan PHP object-oriented code daripada raw SQL. Ini membuat code lebih maintainable dan secure dari SQL injection. File storage menggunakan Laravel's filesystem yang mendukung local disk dan cloud storage (S3, etc).

Eloquent ORM menyediakan abstraction layer yang powerful antara application code dan database. Dengan Eloquent, kita bisa query database menggunakan fluent, expressive syntax seperti Article::where('published_at', '!=', null)->get() instead of raw SQL. Ini bukan hanya membuat code lebih readable, tapi juga automatically protect dari SQL injection karena Eloquent uses parameter binding. Plus, Eloquent's relationship methods membuat working dengan related data jadi sangat straightforward - tanpa perlu manual write JOIN queries.

External Services memperkaya functionality. Google Cloud Translation API enable auto-translation sehingga admin tidak perlu manual translate semua konten. Google Analytics memberikan insights tentang traffic dan user behavior. Schema.org structured data membantu mesin pencari memahami konten untuk better SEO.

Integration dengan external services ini carefully designed dengan fallback mechanisms. Jika Google Translation API down atau quota exceeded, system gracefully degrade - admin masih bisa save content (hanya satu bahasa), dan translation bisa di-retry later. Google Analytics data di-cache dengan TTL 1 hour, meaning jika API unreachable, kita masih serve cached data instead of showing errors. Schema.org implementation using SchemaService yang generate JSON-LD structured data, helping search engines better understand page content dan potentially earning rich snippets in search results.

✨ Fitur-Fitur Utama

1. 🌍 Multi-Language System dengan Auto-Translation

Konsep Dasar

Salah satu fitur unggulan sistem ini adalah dukungan multi-bahasa yang intelligent. Setiap konten dinamis di website dapat ditampilkan dalam dua bahasa: Indonesia dan Inggris. Yang membuatnya special adalah admin tidak perlu manually translate semua konten - sistem melakukannya otomatis menggunakan AI.

Fitur ini sangat penting dalam konteks bisnis klinik medis di Bali, yang melayani baik wisatawan mancanegara maupun pasien lokal. Dengan dukungan dua bahasa, klinik dapat menjangkau audience yang lebih luas tanpa harus menambah beban kerja tim admin untuk melakukan penerjemahan manual yang memakan waktu dan berpotensi inconsistent.

Bagaimana It Works

Ketika admin membuat konten baru (misalnya artikel kesehatan), mereka cukup menulis dalam bahasa Indonesia saja. Sistem kemudian secara otomatis mendeteksi bahwa terjemahan Inggris belum tersedia, lalu memanggil Google Cloud Translation API untuk menerjemahkannya. Hasil terjemahan disimpan di database dan di-cache selama 30 hari untuk efisiensi.

Proses auto-translation ini terjadi secara seamless di background. Admin tidak perlu melakukan aksi tambahan apapun - cukup save artikel dalam satu bahasa, dan sistem langsung menyediakan versi bahasa lainnya dalam hitungan detik. Hasil terjemahan kemudian di-cache dengan TTL (Time To Live) 30 hari untuk menghindari API calls berulang yang sama, menghemat biaya dan meningkatkan response time.

Struktur Data

Semua field yang translateable disimpan dalam format JSON. Pendekatan ini dipilih karena kesederhanaannya - kita tidak perlu membuat separate translation tables atau pivot tables yang akan mengkomplicasi query dan relationship. Dengan JSON, semua translations untuk satu entity tersimpan dalam satu row, membuat query lebih straightforward dan performant.

{
  "title": {
    "id": "Layanan Darurat 24 Jam",
    "en": "24 Hour Emergency Service"
  }
}

Spatie Laravel Translatable package menghandle JSON parsing secara otomatis. Ketika kita akses $service->title di blade template, package otomatis return text sesuai locale yang active. Package ini menggunakan Laravel's localization system, sehingga switching language bisa dilakukan dengan simple app()->setLocale('en').

Flow Auto-Translation Lengkap

Mari kita breakdown step-by-step bagaimana auto-translation bekerja dari saat admin create content hingga user melihat translated version:

1. Admin buat artikel, isi konten Bahasa Indonesia saja
   ↓
2. System detect field English kosong
   ↓
3. Panggil TranslationService->translate()
   ↓
4. Service check cache dulu (key = hash dari text)
   ↓
5a. Cache HIT → Return instantly (<1ms)
5b. Cache MISS → Call Google Cloud API (~500ms)
   ↓
6. Save translation result ke cache (TTL 30 days)
   ↓
7. Return translation ke controller
   ↓
8. Controller save ke database (both languages)
   ↓
9. User bisa switch language di website

Caching strategy yang diterapkan sangat crucial untuk performance dan cost optimization. Google Cloud Translation API mencharge per character yang ditranslate - dengan caching 30 hari, kita avoid redundant API calls untuk text yang sama. Misalnya jika "Layanan Darurat 24 Jam" sudah pernah ditranslate, semua request berikutnya untuk text yang sama akan instantly return dari cache tanpa hit API.

2. 📊 Trend Score System

⚠️ Penting: Trend score calculation menggunakan formula berbasis Google Trends, Analytics, dan Freshness - BUKAN view count!

Problem yang Diselesaikan: Bagaimana menentukan artikel mana yang harus muncul paling atas? Jika sorting hanya by views, artikel lama selalu dominan karena accumulated views. Jika sorting hanya by date, artikel bagus tapi lama jadi terkubur di page 2 atau 3. Sistem butuh intelligent ranking yang menggabungkan beberapa faktor: popularitas global (Google Trends), performa di website sendiri (Analytics), dan kesegaran konten.

Ini adalah challenge klasik dalam content management - bagaimana balance antara "evergreen content" yang selalu relevan dengan "trending topics" yang sedang hot. Pure view count biased terhadap old content (artikel yang udah 6 bulan online pasti punya lebih banyak views daripada artikel kemarin). Pure date sorting biased terhadap new content (artikel kemarin yang low quality bisa muncul di atas artikel 2 bulan lalu yang excellent). Trend score system solve ini dengan multi-factor algorithm.

Solution: Sistem menggunakan TrendAnalysisService yang mengkalkulasi score berdasarkan 3 komponen:

Formula:
trend_score = Google Trends Score + Analytics Score + Freshness Score

Dimana:
- Google Trends Match → +50 points
- Analytics Popularity → +30 points
- Fresh Content (<7d) → +10 points

Maximum possible score: 90 points
📍 Sumber Formula: Formula ini bukan nilai arbitrary, tapi diambil langsung dari implementasi source code di app/Services/TrendAnalysisService.php method analyzeAndUpdateScores(). Dalam code, sistem melakukan penjumlahan bertahap: $score += 50 (Google Trends), $score += 30 (Analytics), $score += 10 (Freshness). Bobot (50, 30, 10) ditentukan berdasarkan prioritas bisnis: Google Trends paling penting karena mencerminkan minat global, Analytics kedua karena menunjukkan performa lokal, and Freshness sebagai bonus kecil untuk konten baru.

Komponen Detail:

  1. Google Trends Score (+50) - Service memanggil Google Trends API untuk mendapatkan trending health keywords. Jika title artikel mengandung trending keyword → +50 points
  2. Analytics Popularity Score (+30) - Service mengambil data dari Google Analytics untuk pages dengan traffic tertinggi. Jika slug artikel match dengan popular page → +30 points
  3. Freshness Score (+10) - Artikel yang dipublish dalam 7 hari terakhir → +10 points. Memberi boost untuk konten fresh agar tidak langsung terkubur

🎯 Mengapa Bobot 50-30-10?

Pemilihan bobot ini bukan nilai sembarangan, tapi berdasarkan reasoning logis dan prioritas bisnis:

1. Google Trends Score = +50 (Tertinggi - 55% dari total)

Mengapa paling tinggi?
• Scope Global: Mencerminkan minat pencarian di seluruh dunia, bukan hanya lokal
• Data Objektif External: Berasal dari Google, sangat reliable dan real-time
• SEO Impact Terbesar: Artikel yang match dengan trending keywords punya potensi traffic organic tertinggi
• User Intent Validation: Jika banyak orang search keyword tertentu, berarti ada demand nyata

Contoh: Jika "Vitamin D" trending di Google Trends, artikel tentang Vitamin D berpotensi mendapat traffic besar dari search engine.
2. Analytics Popularity Score = +30 (Menengah - 33% dari total)

Mengapa lebih rendah dari Trends?
• Scope Lokal: Hanya mencerminkan traffic di website LMC sendiri, bukan global
• Limited Data: Tergantung seberapa banyak traffic website sudah ada
• Bias terhadap Old Content: Artikel lama naturally punya accumulated views lebih banyak
• Complementary: Melengkapi Trends dengan data internal, bukan faktor primary

Tapi tetap penting karena: Menunjukkan apa yang resonates dengan audience spesifik klinik. Artikel mungkin tidak trending globally, tapi sangat popular untuk visitor kita.

Contoh: Artikel "Tips Kesehatan di Bali" mungkin tidak trending global, tapi sangat popular untuk visitor website klinik yang di Bali.
3. Freshness Score = +10 (Terendah - 11% dari total)

Mengapa paling rendah?
• Bukan Indikator Quality: Konten baru ≠ konten bagus
• Temporer Boost Only: Hanya aktif 7 hari, bukan permanent factor
• Prevent Gaming: Jika terlalu tinggi, admin bisa gaming system dengan terus publish artikel baru berkualitas rendah
• Purpose: Hanya untuk "give new content a fair chance" sebelum punya accumulated views

Tapi tetap ada karena: New content perlu exposure awal untuk build momentum. Tanpa boost, artikel baru akan terkubur oleh artikel lama yang sudah punya analytics data.
📊 Ratio Simplified: 5:3:1

Jika disederhanakan, ratio bobot adalah 5:3:1 (Trends:Analytics:Freshness).

Ini adalah weighted scoring system yang common di ranking algorithms:
• Google Search uses 200+ ranking factors dengan bobot berbeda
• YouTube ranking: watch time (tinggi) + likes (menengah) + recency (rendah)
• Reddit: upvotes (tinggi) + engagement (menengah) + time decay (rendah)

Kenapa bukan equal weight (33-33-33)?
Freshness akan terlalu powerful → Low quality new articles bisa beat high quality old articles. Tidak ada clear priority → Sulit predict mana artikel yang akan rank tinggi.

Kesimpulan: Bobot 50-30-10 adalah business decision yang balance antara external validation (Google Trends - most important), internal performance (Analytics - important), dan recency bias (Freshness - nice to have).

3. 📉 Analisis Tingkat Pentalan (Bounce Rate) Tinggi

Apa itu Bounce Rate? Bounce rate atau tingkat pentalan adalah persentase pengunjung yang langsung meninggalkan website setelah melihat satu halaman saja - tanpa berinteraksi, tanpa mengklik link lain, tanpa menjelajah lebih jauh. Tingkat pentalan tinggi (>50%) adalah tanda bahaya yang menunjukkan ada masalah dengan kualitas konten, pengalaman pengguna, atau relevansi.

Ketika pengguna mendarat di artikel "Tips Menurunkan Kolesterol" tapi langsung menutup tab dalam 5 detik, itu dihitung sebagai bounce. Kemungkinan alasan: (1) Konten tidak sesuai ekspektasi dari judul/cuplikan, (2) Kualitas konten buruk (konten tipis, kesalahan tata bahasa), (3) Halaman terlalu lambat dimuat, (4) Desain tidak ramah mata (dinding teks tanpa gambar), atau (5) Tidak ada ajakan bertindak yang jelas untuk menjelajah lebih lanjut.

Implementasi dalam LMC: Sistem secara otomatis melacak dan menandai artikel dengan tingkat pentalan >50% menggunakan data Google Analytics 4. Service GoogleAnalyticsService@getHighBouncePages() mengambil 10 artikel teratas dengan tingkat pentalan tertinggi, lalu menampilkan peringatan di dashboard admin.

⚠️ Mengapa Ini Penting:
Tingkat pentalan tinggi berdampak langsung pada peringkat SEO. Google mengartikan bounce rate tinggi sebagai sinyal bahwa konten tidak memenuhi maksud pengguna - hasilnya? Peringkat pencarian lebih rendah. Selain itu, bounce rate tinggi berarti kehilangan peluang untuk mengubah pengunjung menjadi pasien atau membangun kepercayaan dengan merek klinik.

Implementasi Teknis:

// GoogleAnalyticsService.php
public function getHighBouncePages(int $limit = 10): array
{
    return Cache::remember('ga4_high_bounce', 3600, function () use ($limit) {
        $period = Period::days(30);
        
        // Fetch page views dengan engagement metrics dari GA4
        $response = Analytics::get(
            $period,
            ['screenPageViews', 'bounceRate', 'engagementRate'],
            ['pagePath'],
            $limit * 2
        );
        
        $highBouncePages = [];
        
        foreach ($response as $row) {
            $pagePath = $row['pagePath'] ?? '';
            $bounceRate = floatval($row['bounceRate'] ?? 0);
            
            // Filter: Only article pages dengan bounce rate > 50%
            if ($bounceRate > 0.5 && str_contains($pagePath, '/articles/')) {
                $highBouncePages[] = $pagePath;
            }
            
            if (count($highBouncePages) >= $limit) break;
        }
        
        return $highBouncePages;
    });
}

Tindakan untuk Admin: Ketika artikel ditandai memiliki bounce rate tinggi, admin harus menyelidiki dan meningkatkan konten. Tindakan yang bisa dilakukan: (1) Tulis ulang paragraf pembuka untuk langsung menarik perhatian pembaca, (2) Tambahkan gambar/infografis yang menarik, (3) Pecah dinding teks menjadi bagian-bagian yang mudah dipindai dengan subjudul, (4) Tambahkan tautan internal ke artikel terkait, (5) Sertakan ajakan bertindak yang jelas seperti "Baca artikel terkait" atau "Hubungi kami untuk konsultasi".

Strategi Caching: Data di-cache selama 1 jam. Bounce rate tidak berubah secara drastis setiap menit, jadi pembaruan setiap jam sudah cukup untuk menyeimbangkan antara data terbaru dan efisiensi API.

4. 📊 Analisis Penurunan & Pertumbuhan Konten

Penjelasan Content Decay: Content decay atau penurunan konten terjadi ketika artikel yang dulu populer secara bertahap kehilangan traffic seiring waktu. Ini adalah fenomena alami - informasi menjadi usang, kompetitor menerbitkan konten yang lebih baik, atau tren pencarian berubah. Tanpa pemantauan, artikel bisa secara diam-diam turun dari 1000 views/bulan menjadi 100 views/bulan tanpa ada yang menyadari.

Contoh nyata: Artikel "Panduan Vaksin COVID-19" mungkin sangat populer di 2021-2022 (puncak pandemi), tapi di 2026 traffic-nya turun signifikan karena: (1) Pandemi sudah mereda, minat menurun, (2) Informasi sudah usang (jenis vaksin berubah), (3) Perilaku pencarian pengguna berubah (dari "apakah vaksin aman?" ke "jadwal booster"). Jika admin tidak menyadari penurunan ini, artikel yang berharga menjadi "konten zombie" - ada tapi tidak produktif.

Pertumbuhan Konten: Sebaliknya, pertumbuhan konten adalah ketika artikel mengalami peningkatan traffic. Bisa karena: (1) Topik tiba-tiba trending (misalnya "Demam Berdarah" saat wabah), (2) Peringkat artikel meningkat di hasil pencarian, atau (3) Dibagikan secara viral di media sosial. Pertumbuhan adalah peluang untuk dimanfaatkan - mungkin membuat lebih banyak konten terkait atau mengoptimalkan artikel lebih lanjut.

Perbandingan Bulan-ke-Bulan: Sistem membandingkan traffic 30 hari terakhir dengan 30 hari sebelumnya (30-60 hari yang lalu) untuk menghitung persentase perubahan. Formula sederhana tapi efektif:

Formula Perubahan Traffic:
perubahan% = ((views_bulan_ini - views_bulan_lalu) / views_bulan_lalu) × 100

Klasifikasi Status:
- 📈 Bertumbuh: perubahan > 0% (traffic meningkat)
- ✅ Stabil: -30% ≤ perubahan ≤ 0% (fluktuasi kecil, normal)
- ⚠️ Peringatan Penurunan: perubahan < -30% (penurunan signifikan, perlu tindakan!)

Contoh:
Bulan Lalu: 800 views | Bulan Ini: 500 views
Perubahan = ((500 - 800) / 800) × 100 = -37.5%
Status: ⚠️ Peringatan Penurunan
📍 Sumber Formula: Formula persentase perubahan ini adalah rumus matematika standar yang digunakan universal dalam statistik dan analisis bisnis. Dalam project LMC, implementasinya ada di app/Services/GoogleAnalyticsService.php method calculateTrafficChange() baris 84: $change = (($currentViews - $lastViews) / $lastViews) * 100.

Mengapa threshold -30%? Penurunan 0% sampai -30% dianggap "Stabil" karena traffic website selalu berfluktuasi secara natural (10-20% naik turun adalah normal). Threshold -30% dipilih untuk membedakan antara "fluktuasi normal" vs "masalah serius yang perlu tindakan". Hanya penurunan lebih dari 30% yang dianggap content decay signifikan.

Pemantauan Otomatis:

Sistem menjalankan analisis penurunan konten secara otomatis setiap minggu melalui Laravel Scheduler. Cron job menjalankan perintah php artisan seo:check-decay setiap Senin jam 8 pagi, menghasilkan laporan komprehensif dari semua artikel yang dipublikasikan.

// routes/console.php
Schedule::command('seo:check-decay')->weeklyOn(1, '08:00');

// CheckContentDecayCommand.php
public function handle(GoogleAnalyticsService $analytics)
{
    $articles = Article::whereNotNull('published_at')->get();
    
    foreach ($articles as $article) {
        $path = "/articles/{$article->id}";
        
        // Calculate month-over-month traffic change
        $change = $analytics->calculateTrafficChange($path);
        
        // Determine status
        if ($change < -30) {
            $status = '⚠️ Decay Alert';
            Log::warning("Content Decay: {$article->title} dropped {$change}%");
        } elseif ($change > 0) {
            $status = '📈 Growing';
        } else {
            $status = '✅ Stable';
        }
        
        // Results displayed in CLI table
        $results[] = [
            'Title' => $article->title,
            'Change' => $change.'%',
            'Status' => $status
        ];
    }
}

Integrasi Dashboard Admin: Data penurunan/pertumbuhan juga ditampilkan di dashboard analytics admin dalam format tabel visual. Admin bisa langsung melihat artikel mana yang perlu perhatian (peringatan penurunan) dan artikel mana yang berkinerja baik (traffic bertumbuh). Ini mengubah analytics dari angka pasif menjadi wawasan yang dapat ditindaklanjuti.

Strategi Perbaikan untuk Konten yang Menurun: Ketika artikel diklasifikasikan sebagai menurun, admin punya beberapa pilihan: (1) Perbarui & Segarkan - Tambahkan informasi baru, perbarui statistik, segarkan bagian yang usang, (2) Tingkatkan SEO - Optimalkan judul/deskripsi meta, tambahkan kata kunci yang hilang, tingkatkan tautan internal, (3) Ubah Tujuan - Ubah menjadi konten video atau infografis, (4) Gabungkan - Gabungkan dengan artikel terkait menjadi panduan komprehensif, atau (5) Pensiunkan - Jika benar-benar usang, ubah ke draft atau tambahkan redirect ke versi yang diperbarui.

Dampak Bisnis: Dengan pemantauan penurunan konten yang proaktif, klinik dapat mempertahankan portofolio konten yang lebih sehat. Alih-alih membiarkan traffic perlahan berkurang, admin dapat dengan cepat melakukan intervensi dan merevitalisasi konten. Hasilnya? Traffic organik yang berkelanjutan, peringkat pencarian yang lebih baik, dan aliran berkelanjutan calon pasien yang menemukan klinik melalui pencarian.

5. 📝 Content Management System (CMS)

CMS memungkinkan admin manage ALL website content tanpa touching code. Semua operations dilakukan through user-friendly forms.

Modules:

  • Header Management: Title, Tagline, Logo (image), Button Text
  • About Management: Title, Description, Vision, Mission, Image
  • Contact Management: Address, Phone, Email, WhatsApp, Social Media, Google Maps Embed
  • Services CRUD: Full Create-Read-Update-Delete untuk layanan medis
  • Doctors CRUD: Manage doctor profiles dengan Name, Specialty, Bio, Photo
  • Articles CRUD + Publishing: Rich text editor, featured image, draft/publish system
  • Gallery CRUD: Upload photos dengan sort order dan active/inactive toggle

4. 🔐 Role-Based Access Control (RBAC)

Sistem memiliki dua roles:

  • Owner: Full access termasuk user management
  • Admin: Content management only, no user access
Fitur Owner Admin
Dashboard ✅ ✅
Manage Content (Header, About, Contact) ✅ ✅

🗄️ Penjelasan Database

Overview Struktur

Database LMC terdiri dari 9 tabel utama, dirancang dengan prinsip normalization tapi tidak over-normalized untuk maintain performance. Tidak ada foreign key constraints yang kompleks - ini design choice untuk simplicity karena relationship antar entities tidak strict.

Tabel-Tabel dan Penjelasannya

1. users

Purpose: Menyimpan data admin dan owner yang bisa login ke admin panel.

Key Fields:

  • id - Primary key auto-increment
  • name - Full name user
  • email - Unique email for login
  • password - Bcrypt hashed password
  • role - ENUM('owner', 'admin') - Menentukan permission level
  • email_verified_at - NULL jika email belum verified

2. headers, contacts, abouts

Pattern: Singleton tables (hanya boleh 1 record). Semua text fields disimpan dalam format JSON untuk multi-language support.

💡 Why JSON?
JSON allows us menyimpan multiple languages dalam satu field, making queries simpler dan avoiding need untuk separate translation tables.

3. services, doctors, galleries

Pattern: Multiple records tables dengan JSON fields untuk translatable content.

4. articles

Most Complex Table karena punya draft/publish system dan trending algorithm.

Key Fields:

  • title, excerpt, content - JSON multi-language
  • image - Featured image path
  • slug - URL-friendly identifier
  • published_at - NULL = draft, timestamp = published
  • view_count - Incremented each view
  • trend_score - Calculated score untuk sorting
  • trend_data - JSON untuk debugging (stores which factors contributed to score)

5. search_logs

Purpose: Analytics - track all search queries.

Fields:

  • query - Keyword yang dicari
  • results_count - Berapa artikel found
  • ip_address - User IP
  • created_at - When searched
Use Case: Top missing keywords analysis
Query untuk find keywords yang sering dicari tapi zero results:
SELECT query, COUNT(*) as searches FROM search_logs WHERE results_count = 0 GROUP BY query ORDER BY searches DESC LIMIT 5

2. Content Creation Flow (Article Example)

Phase 1: Draft Creation

  1. Admin navigasi ke /admin/articles/create
  2. Admin isi form (Title & Content in ID only, leave EN empty)
  3. Admin klik "Save as Draft"
  4. POST request ke /admin/articles
  5. Controller validate input via StoreArticleRequest
  6. TranslationHelper::autoTranslateFields() deteksi EN kosong
  7. TranslationService called → Check cache → Call Google API → Return translation
  8. Article created dengan published_at = NULL (DRAFT)

Phase 2: Publishing

  1. Admin edit artikel draft
  2. Set Published At = "2026-02-01 10:00:00"
  3. PUT request ke /admin/articles/{id}
  4. Controller update published_at
  5. Artikel sekarang LIVE di landing page!

Phase 3: Trend Score Calculation

  1. Cron job run setiap hari (scheduled task)
  2. TrendAnalysisService@analyzeAndUpdateScores() called
  3. Service fetch:
    • Google Trends: ['Vitamin C', 'Flu', ...]
    • Analytics: ['/articles/vitamin-c', ...]
  4. Loop semua artikel:
    • Check title match trending keyword → +50
    • Check slug di Analytics → +30
    • Check freshness < 7 days → +10
  5. Update trend_score di database

Article Lifecycle

PHASE 1: CREATION
  Admin → /admin/articles/create → Fill Form → Submit
  ↓
  Validation → Auto-translate → Article::create()
  ↓
PHASE 2: DRAFT STATE
  published_at = NULL
  Visible in admin panel only
  NOT visible on landing page
  ↓
PHASE 3: PUBLISHED STATE
  Admin set published_at = now()
  NOW visible on landing page
  trend_score = 0 (waiting cron)
  ↓
PHASE 4: TRENDING STATE
  Cron job → TrendAnalysisService
  Calculate score (Google Trends + Analytics + Freshness)
  Update trend_score
  Article appears at top of landing page
  ↓
PHASE 5: MATURE STATE
  Article > 7 days (lose freshness bonus)
  Keyword not trending (lose trends bonus)
  Traffic down (lose analytics bonus)
  Score decreases, article position drops

💡 Logika Bisnis Penting

1. Singleton Pattern untuk Settings Tables

Problem: Headers, contacts, dan abouts hanya boleh punya 1 record. Multiple records akan cause confusion.

Solution: Enforce singleton pattern di Model level via boot() method.

2. Draft vs Published Logic

Draft Detection: $isDraft = $article->published_at === null

Query Only Published: Article::whereNotNull('published_at')->get()

Benefits:

  • Admin bisa prepare content in advance
  • Review process sebelum publish
  • Scheduled publishing untuk content calendar

3. Zero Result Search Analysis

Why Important: Setiap zero result search = missed opportunity. User cari info, tidak dapat, kemungkinan besar leave website frustrated.

How It Works:
1. Log EVERY search dengan result count
2. Dashboard analyze top keywords dengan zero results
3. Admin create artikel untuk keywords tersebut
4. Next user yang search dapat hasil → Better UX!

4. Image Optimization

Problem: User upload foto 5MB dari kamera → Website jadi lambat → User bounce

Solution: Auto-resize to max 1200px + compress to 85% quality

Result: Original 5MB → After ~300KB (16x faster!)

5. Cache Strategy untuk Performance

  • Translation Cache: TTL 30 days - Translations never change spontaneously
  • Analytics Cache: TTL 1 hour - Data doesn't change minute-to-minute
  • Trend Keywords Cache: TTL 24 hours - Trends update daily, not real-time

6. Preference Modal UX Pattern

Problem: Website punya banyak sections. User harus scroll manual untuk cari info.

Solution: Show preference modal on first visit → Auto-scroll to selected section

Benefits:

  • Reduce time to relevant content (dari ~30 detik jadi ~2 detik)
  • Better UX & Lower bounce rate
  • Personalized experience

7. Internal Link Service (SEO Boost)

Purpose: Auto-link keywords dalam artikel ke artikel lain yang relevan.

SEO Benefits:

  • Better internal linking structure
  • Helps search engines understand content relationships
  • Increases page authority distribution
  • Encourages users explore more content
